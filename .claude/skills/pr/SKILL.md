# PR をレビューして本文を作る

マージ先: $ARGUMENTS（省略時は `develop`）

`/review` が「書いたコード 1 箇所」を見るのに対し、これは**ブランチ全体**を見る。

## 手順

### 1. 範囲を確定する

```bash
git log --oneline <マージ先>..HEAD
git diff <マージ先>...HEAD --stat
```

コミットが 0 件なら、そこで止めて報告する。

### 2. 検証を実行する。推測で語らない

```bash
npm run typecheck && npm run test && npm run test:types && npm run lint
```

**1 つでも赤ければ、その時点で報告して止める。** 赤いまま PR 本文を作らない。

### 3. 差分を読む

```bash
git diff <マージ先>...HEAD
```

`src/` の変更は必ず全部読む。設定ファイルとドキュメントは変更点だけでよい。

### 4. テンプレートを読む

**`.github/PULL_REQUEST_TEMPLATE.md` を読み、その節構成に従う。** ここに節を書き写さない。テンプレートが変わったら自動的に追従させるため。

### 5. 埋められる欄と、埋められない欄を分ける

**Claude が埋める欄** — 既にある情報から決まるもの。判断が新しく発生しないもの。

- 何をしたか（差分の要約）
- 検証のチェックボックス（実際に走らせた結果のみ。走らせていないものにチェックを入れない）
- 公開 API への影響（下記 6 の調査結果）
- 記録のチェックボックス（下記 7 の調査結果）
- **積み残し** — `LEARNING_LOG.md` の積み残しから、**この PR が触った範囲に関係するものを抜き出す**。判断も時期も既に記録済みなので、選んで並べるだけ。本人に書かせると手で写す作業が増えるだけで、理解の検査にもならない。**PR には結論だけ書き、詳細は `LEARNING_LOG.md` に任せる**（読み手が違う）

  **「やらなかったこと」はこの節に一本化する。** 「なぜそうしたか」の中に同じ内容を書かない。両方に書くと同じ項目が 2 回並ぶ（実際に起きた）
- **なぜそうしたか（記録済みの分）** — この PR の差分で `LEARNING_LOG.md` に追加された記録を拾い、見出しごとリンクする。

  ```bash
  git diff <マージ先>...HEAD -- LEARNING_LOG.md | grep -E "^\+### [DL]-[0-9]+"
  ```

  拾った D-xxx / L-xxx を、**タイトルと 1 行要約付きで**並べる。リンクを写すのは機械的な作業で、理解の検査にならない。
  **記録に無い理由だけを本人に残す。** 該当が無ければ「記録済みの分で尽きているか」を確認する 1 行を添える

**本人が埋める欄** — 判断の主体が本人でなければならないもの。空欄のまま渡し、「ここは自分で書いてください」と明示する。

- **なぜそうしたか（記録に無い分）** — `LEARNING_LOG.md` のどこにも書かれていない判断。**PR の分け方、スコープの決め方、この PR 固有の事情**など。ここが埋まらないなら、**そもそも記録漏れの疑い**として手順 7 で拾うべきだった可能性がある
- **原則との突き合わせ** — 「満たした」と判断するのは実装者の責任。Claude がチェックを入れると保証の主体がすり替わる。該当しそうな原則の見当を示すところまで
- **テストが効いていることの確認** — 変異テストを実際に回したかは本人しか知らない。Claude が代わりに回した場合は、**何をどう壊して赤くなったかを事実として書く**（チェックは入れない）

判断に迷ったら「**この欄を埋めるのに新しい判断が要るか**」で分ける。要らないなら Claude が埋める。

### 6. 公開 API の変更を洗い出す

差分から次を機械的に拾う。

- `src/index.ts` の export の増減
- `hozo-` で始まるクラス名の追加・変更・削除
- `data-` で始まる属性の追加・変更・削除

いずれも `LEARNING_LOG.md` の D-006 で公開 API と定めたもの。**変更があれば破壊的変更の候補として明示する。**

### 7. 記録漏れを調べる

- `src/` に変更があるのに `LEARNING_LOG.md` が変わっていない → 学習記録または設計判断が要るか確認を促す
- 型定義（`*.types.ts` / `src/types/`）が変わっているのに `docs/error-messages/` が変わっていない → エラーメッセージの再採取が要るか確認を促す

**「要る」と決めつけない。** 設定変更やリファクタなら不要なこともある。

### 8. タイトルを提案する

コミットメッセージと同じ Conventional Commits の形にする（`git log` の既存の形に合わせる）。

- **`type` は PR 全体で最も価値のある変更で決める。** コミット数の多さではない。`docs:` のコミットが 10 件あっても、`feat:` が 1 件あれば `feat:`
- **スコープではなく、何ができるようになったかを書く。** 「Button を修正」ではなく「Button を as で要素差し替え可能にする」
- 70 文字を目安にする。長い補足は本文の「何をしたか」に回す
- 変更が 2 種類以上混ざっている場合は、**タイトルを付けにくいこと自体を PR 分割の判断材料として報告する**

候補を 2〜3 個出し、推奨と理由を添える。

### 9. 報告する

まず所見、次にタイトル案、最後に PR 本文の下書き。

## 報告の形

````
## 検証結果
typecheck:  <pass/fail>
test:       <pass/fail>（N tests）
test:types: <pass/fail>（N tests）
lint:       <pass/fail>

## 差分の範囲
<コミット数とファイル数。主要な変更を 3 行以内で>

## 指摘
<マージ前に直すべきもの。無ければ「なし」>

## 公開 API の変更
<型 / クラス名 / data-* の増減。無ければ「なし」>

## 記録の状態
<LEARNING_LOG.md と docs/ の更新有無。漏れの疑いがあれば指摘>

---

## タイトル案
<候補 2〜3 個。推奨と理由>

---

## PR 本文の下書き

```markdown
<テンプレートの節構成に従った本文。本人が埋める欄は
<!-- ここは自分で書く --> を残す>
```
````

## 厳守

- **確認していないことを「確認済み」と書かない。** 実行した検証だけをチェックする
- **「なぜそうしたか」のうち、記録に無い分を代筆しない。** `LEARNING_LOG.md` に書かれている理由はリンクで示してよい（写す作業に検査の意味は無い）。**記録のどこにも無い判断を推測で書かない**
- 原則との突き合わせは、**該当しそうな原則を挙げるところまで**。チェックは本人が入れる
- 修正版のコードを書かない。`/review` と同じく問題の所在だけ示す
- `src/` を編集しない
- **PR を作成しない。** `gh pr create` を実行しない。本文を渡すところまでが仕事で、出すかどうかは本人が決める
- テンプレートの節を勝手に増減しない。テンプレート自体を変えたいときは、その旨を別途提案する
