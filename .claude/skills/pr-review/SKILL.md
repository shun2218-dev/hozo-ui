# PR をレビューしてコメントする

対象 PR: $ARGUMENTS（省略時は現在のブランチに紐づく PR）

`/pr` が**出す前**の下書き作成、これは**出した後**のレビューとコメント投稿。

## 手順

### 1. 対象を特定する

```bash
gh pr view $ARGUMENTS --json number,title,state,baseRefName,headRefName,url
```

PR が見つからなければ、そこで止めて報告する。`/pr` で本文を作って先に出すよう促す。

### 2. 検証を実行する。推測で語らない

レビュー対象のブランチがローカルに無い、または現在のブランチと違う場合:

```bash
gh pr checkout <番号>
```

**チェックアウトは作業ツリーを変える操作なので、未コミットの変更があるときは実行前に確認を取る。**

```bash
npm run typecheck && npm run test && npm run test:types && npm run lint
```

赤があれば、それ自体が最優先の指摘になる。

### 3. 差分を読む

```bash
gh pr diff <番号>
```

`src/` の変更は全部読む。行番号が要るので、`--patch` の出力をそのまま使う。

### 4. レビューする

観点は `/review` と同じ。加えて PR 単位でしか見えないものを見る。

- **`CONCEPT.md` の原則 1〜6 との突き合わせ**（特に原則 6 — 削れる型は無いか）
- **公開 API の変更** — `src/index.ts` の export、`hozo-` クラス名、`data-*` 属性。D-006 で公開 API と定めたもの
- **テストが効いているか** — 新しいテストがあれば、**実際に壊して赤くなるか確かめる**。一時ファイルで変異版を作って検証してよい（`src/` は編集しない）
- **記録漏れ** — `src/` が変わったのに `LEARNING_LOG.md` が、型が変わったのに `docs/error-messages/` が更新されていないか
- **PR 本文がテンプレートの節を埋めているか** — 特に「なぜそうしたか」が空でないか

### 5. 指摘を 2 種類に分ける

| 種類 | 条件 | 投稿方法 |
|---|---|---|
| **行に紐づく指摘** | 差分の特定の行が問題 | inline コメント |
| **全体への指摘** | 設計判断、記録漏れ、複数箇所にまたがるもの | レビュー本文 |

行を特定できるものを本文にまとめない。**読み手が場所を探すことになる。**

### 6. 投稿前に全文を見せて承認を得る

**これは外部に公開される行為なので、承認なしに投稿しない。**

投稿予定の内容をすべて提示する。

- レビュー本文（全体への指摘）
- inline コメント（ファイル・行・本文）

「この内容で投稿しますか」と聞き、明確な同意を得てから 7 に進む。修正の指示があれば直して再提示する。

### 7. 投稿する

全体への指摘のみの場合:

```bash
gh pr review <番号> --comment --body "<本文>"
```

inline コメントを含む場合は、REST API を使う。

```bash
gh api repos/{owner}/{repo}/pulls/<番号>/comments \
  -f body="<本文>" \
  -f commit_id="<HEAD の SHA>" \
  -f path="<ファイルパス>" \
  -F line=<行番号> \
  -f side="RIGHT"
```

`commit_id` は `gh pr view <番号> --json headRefOid` で取る。

**`--approve` と `--request-changes` は使わない。** GitHub は自分の PR を承認できないため失敗する。他者の PR でも、承認は本人の判断なので Claude が代行しない。

### 8. 投稿結果を報告する

投稿した URL を示す。失敗したものがあれば、どれが失敗したかを明示する。**一部だけ成功した状態を黙って報告しない。**

## 厳守

- **承認を得るまで投稿しない。** `gh pr review` / `gh api ... comments` は 6 の同意を得てから
- **`--approve` / `--request-changes` を使わない**
- **`gh pr merge` を実行しない。** マージは本人の判断
- 修正版のコードを書かない。「ここが問題です、どう直しますか」で止める
- `src/` を編集しない。変異テストは一時ファイルで行い、終わったら消す
- **確認していないことを指摘に書かない。** 実行した検証の結果だけを根拠にする
- 指摘が無ければ「指摘なし」と報告する。**コメントを埋めるために指摘を作らない**
- 良い点は理由込みで。お世辞は書かない
