# エラーメッセージの記録

CONCEPT.md **原則 3 — エラーメッセージは API の一部である** の実作業。

型が通らないときのメッセージを採取し、読みやすさをレビュー対象にする。ここに記録が無い型は、原則 3 の観点で未検証とみなす。

---

## 粒度

| 単位 | 決定 |
|---|---|
| ファイル | **コンポーネント 1 つにつき 1 ファイル**（`button.md`, `select.md` …） |
| セクション | **「利用者がやりがちな誤り」1 つにつき 1 セクション** |

コンポーネント単位にする理由は、原則 3 のレビューが「この API のエラーは読めるか」という単位で行われるため。エラー単位でファイルを切ると増えすぎ、全体で 1 ファイルにすると Select・Field を書いた時点で破綻する。

外部ライブラリのエラーは、自作の型と混ざらないよう各ファイルの末尾に「参考」として置く。

---

## 記録フォーマット

````markdown
### E-000 | <誤りの内容を一行で>

**書いたコード**

```tsx
<Button ... />
```

**エラー全文**

```
（省略せずに貼る。... で畳まれた部分もそのまま残す）
```

- **行数**:
- **読めるか**: ◎ / ○ / △ / ✕
- **利用者は原因に辿り着けるか**:
- **改善案**:
````

### 想定読者

評価は次の人物を基準に行う。

> **TypeScript を日常的に書いているが、Hozo UI の内部型定義は読んでいない人。**

「型を知らない人に分かるか」は基準にしない。到達不可能であり、TypeScript を採用している前提と矛盾するため。判定すべきは、**利用者の手元にある情報（エラー本文と発生位置）だけで直し方に到達できるか**。内部の型名を名指しされても照合先が無いなら、それは欠陥として数える。

### 「読めるか」の基準

| 記号 | 意味 |
|---|---|
| ◎ | 1 行目だけで原因が分かる |
| ○ | 全文を読めば分かる |
| △ | 発生位置と併せて読めば分かる。本文だけでは足りない |
| ✕ | 読んでも分からない。設計の欠陥として扱う |

△ 以下は **union の設計変更・ブランド型・ヒント型の混入**を検討する対象。改善したら記録を更新し、変更前後を残す。

---

## 採取手順

1. わざと誤ったコードを書く（`src/` の型テストに一時的に置く、または別ファイル）
2. `npm run typecheck` の出力をそのままコピーする
3. **省略しない。** `... 287 more ...` のような畳み込みも含めて貼る。読めなさ自体が記録対象
4. 誤ったコードは記録後に戻す（型テストとして残すなら `@ts-expect-error` か `expectTypeOf().not` を添える）

エディタのホバー表示ではなく **`tsc` の出力**を使う。利用者が CI で見るのはこちら。
